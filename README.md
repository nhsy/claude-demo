# vault-posture

> **READ-ONLY.** This skill never changes Vault: it never writes, cancels, rotates, patches, registers or tunes anything, never mints tokens, and never runs the fixes it drafts. An operator runs them.

A read-only HashiCorp Vault **security posture** review skill for Claude Code, packaged as a plugin. It complements [vault-ops](https://github.com/nhsy-hcp/vault-ops-skill): vault-ops asks *"is the cluster running well?"*, vault-posture asks *"is it configured safely?"*.

A single-file `uv run --script` Python program (`hvac`, `requests`, `cryptography`) reads Vault with HTTP GET only and writes small JSON files. Claude reads them, explains the findings and drafts fixes as text. Skill usage, setup and the rule list are in [`skills/vault-posture/README.md`](skills/vault-posture/README.md).

## What it checks

| Subcommand | Rules | Looks at |
| --- | --- | --- |
| `roles` | VP-ROLE-001..009, VP-AWS-001..004, VP-GCP-001..004, VP-AZURE-001..003, VP-CERT-001..002 | JWT/OIDC, Kubernetes, AWS, GCP, Azure, cert, AppRole and token roles in every namespace: root via login, audience-only or wildcard JWT bindings, any-pod Kubernetes roles, any-account AWS IAM and EC2 roles, any-project GCP IAM and GCE roles, long-lived GCP signed JWTs, tenant-wide Azure roles, unconstrained or catch-all cert roles, role-ID-only AppRoles, never-expiring secret IDs, unbounded periodic tokens |
| `pki` | VP-PKI-001..008 | Issuer expiry, weak CA keys, AIA/CRL/OCSP, auto-tidy, leaves outliving the CA (needs the PKI add-on policy) |
| `quotas` | VP-QUOTA-001..004 | Missing or path-only rate-limit and lease-count quotas, unaudited throttling |
| `security` | VP-SEC-001..004, VP-PLUG-001..002 | Root/recovery token generation or rekey in progress, barrier key age and rotation, external plugins |
| `audit` | all live rules | One combined `*-posture-*.json` |
| `access` | offline | "Who can do X on path Y" from ACL policy files, using Vault's matching rules (checked against `sys/capabilities`) |
| `diff` | offline | "What changed since the last review": new, resolved and unchanged findings between two result files, by fingerprint |

The catalogue with remediation is [`skills/vault-posture/references/rules.md`](skills/vault-posture/references/rules.md).

## Quick start

```text
/plugin marketplace add nhsy/claude-demo
/plugin install vault-posture@vault-posture-skill
```

```bash
# once, by an admin (root namespace)
vault policy write vault-posture-readonly skills/vault-posture/policies/vault-posture-readonly.hcl
vault policy write vault-posture-pki-reader skills/vault-posture/policies/vault-posture-pki-reader.hcl
# each session
export VAULT_ADDR=https://vault.example.com:8200 VAULT_CACERT=/path/to/ca.pem
export VAULT_TOKEN="$(vault token create -policy=vault-posture-readonly -policy=vault-posture-pki-reader -no-default-policy -orphan -ttl=1h -field=token)"
claude   # "review our Vault security posture"
```

## How read-only is enforced

1. **Token policies.** [`vault-posture-readonly.hcl`](skills/vault-posture/policies/vault-posture-readonly.hcl) grants `read`/`list` on exactly the endpoints the script reads, in the root namespace and five namespace levels, and denies credential-minting and AppRole secret endpoints. PKI reads are in the opt-in [`vault-posture-pki-reader.hcl`](skills/vault-posture/policies/vault-posture-pki-reader.hcl). Both are generated by `scripts/gen_policies.py`. This is the hard boundary.
2. **Code.** `Reader` is the script's only route to Vault and only sends GET. Every response is reduced to an allowlist of fields, so role IDs, secret IDs, nonces, OTPs, encoded tokens and certificate PEMs never reach a file.
3. **Skill.** `allowed-tools` pre-approves only the script, and `SKILL.md` forbids running remediation even when asked. For defence in depth, also deny `Bash(vault write:*)`, `Bash(vault delete:*)`, `Bash(vault patch:*)`, `Bash(vault operator:*)` and `Bash(curl:*)` in your Claude Code `permissions.deny`.

## Development

Needs [uv](https://docs.astral.sh/uv/), [Task](https://taskfile.dev) and the [`vault` CLI](https://developer.hashicorp.com/vault/install). Docker or Podman with compose is optional (container dev servers). Everything runs through Task; `task` lists the targets.

```bash
task init                    # uv sync, pre-commit hooks, .env from template
task test                    # unit tests, no Vault needed (coverage gate 90%)
task dev:up seed token       # local `vault server -dev` on :8250, seed findings, mint the read-only token
task test:integration        # live tests with the read-only token
task skill:run -- audit      # run the script by hand
task skill:access -- --policy tests/fixtures/policies --path secret/data/app/x --capability update
task dev:down
task test:e2e                # all of the above on a fresh local dev server
task lint                    # ruff, shellcheck, gitleaks, yaml/json
```

| Dev server | Start | Address |
| --- | --- | --- |
| Local `vault server -dev` (default) | `task dev:up` | `http://127.0.0.1:8250` |
| Community container | `task up` | `http://127.0.0.1:8250` |
| Enterprise container (`VAULT_LICENSE` in `.env`) | `task up:ent` | `http://127.0.0.1:8260` |

All are in-memory dev servers with root token `root`. `task seed` (`scripts/seed_findings.sh`) configures one to trip every rule a dev server can show (quotas, a root generation and a rekey in progress, an unversioned external plugin, loose JWT/Kubernetes/AWS/GCP/Azure/cert/AppRole/token roles, short-lived CAs), plus quiet controls. `task token` writes both policies and mints a 1h token into `.tmp/posture-token`.

### Tests

| File | Covers |
| --- | --- |
| `tests/test_checks.py` | Quota and security rules fire on their trigger and stay quiet on their control; every rule is in `rules.md` |
| `tests/test_roles.py`, `tests/test_pki.py` | Role and PKI rules, expiry windows, certificate parsing |
| `tests/test_access.py` | Policy parsing (HCL, JSON, legacy) and ACL evaluation against results captured from Vault |
| `tests/test_diff.py` | Comparing two runs: new / resolved / unchanged, rotated PKI issuers, mismatch and coverage warnings, schema validation |
| `tests/test_collect.py` | Coverage classification, namespace walking, field allowlisting |
| `tests/test_readonly.py` | Through real hvac/requests with the transport patched: only GET is sent, namespaces go in the header, no token or secret reaches output |
| `tests/test_cli.py` | Output files (0600, `.gitignore`), exit codes, setup errors, schema validation |
| `tests/test_policy.py` | Policies match the generator, grant only read/list, cover every read at every namespace level, keep sensitive paths denied |
| `tests/test_integration.py` | `-m integration`: seeded dev server, all seeded rules fire and controls stay quiet, coverage complete, writes denied, `access` matches `sys/capabilities` |

### Evals

`evals/` holds [`claude plugin eval`](https://code.claude.com) cases: interpreting a saved review, refusing to cancel a root generation, reporting partial PKI coverage, not inventing findings without shell access, not triggering on Terraform authoring or client-count/health questions, interpreting role, PKI and quota findings, and refusing to print credentials (10 cases). `task eval` runs them (uses API credits). `task eval:judge` runs all 10 on Opus, Sonnet and Haiku with one fixed LLM judge (`JUDGE_MODEL`, default sonnet) and writes a side-by-side table to `evals/results/judge/summary.md`. Fixtures are real `audit --redact-addr` output from the seeded dev server.

### CI

`.github/workflows/ci.yml` runs `task lint`, `task plugin:validate`, `task test`, then two e2e jobs in parallel: `integration` runs `task test:e2e` against a local `vault server -dev`, and `compose` runs `task test:e2e:compose` against the Community container in `compose.yaml`.

## Issue pipeline (`/issue-sdlc`)

Claude Code works labelled GitHub issues through the SDLC from your terminal: refine and plan, build, test, self-review, open a draft PR, and fix review feedback. People keep two gates: approving the plan and merging the PR. The project skill [`.claude/skills/issue-sdlc`](.claude/skills/issue-sdlc/SKILL.md) finds the next item in GitHub, runs one stage and stops. Nothing runs on its own: you start every run by typing `/issue-sdlc` (or `/issue-sdlc 42` for one item). There are no GitHub Actions and no CI-hosted agent.

```
agent-ready ─▶ /issue-sdlc plans ─▶ agent-plan-review ─▶ (you comment "Approved") agent-build
            ─▶ /issue-sdlc builds ─▶ draft PR, agent-pr-review ─▶ (you comment, set agent-fix on the PR ⟲ /issue-sdlc fixes)
            ─▶ (you) Rebase and merge, which closes the issue ─▶ next /issue-sdlc run: agent-done
any stage ─▶ agent-blocked (question or failed run) ─▶ answer, then re-add the stage's label (agent-ready, agent-build or agent-fix)
```

Labels, the definition of ready, and branch and commit conventions are in [CLAUDE.md](CLAUDE.md). New work uses the **Agent task** issue form; `/issue-sdlc` fills in the PR template.

**One-time setup** (needs `gh` signed in with admin rights on the repo):

1. `task github:setup`: creates the eight `agent-*` labels with colours and descriptions (rerunning resets them), then checks the merge settings without changing them. If they differ from rebase merging only with automatic head-branch deletion, it prints each setting to change under **Settings → General → Pull Requests**. It uses only the REST API (`gh api`), so it also works where GitHub GraphQL is blocked, as in Claude Code cloud sessions.
2. Protect `main` with a branch protection rule or ruleset that requires a pull request, passing checks and linear history (linear history rejects any PR containing a merge commit). Don't require an approving review while Claude Code works as your GitHub account: it opens PRs as you, GitHub doesn't let you approve your own PR, and every merge would need an admin bypass. Require one once the agent has its own identity (a GitHub App or machine user).
3. In Claude Code: `/plugin install code-review@claude-plugins-official` and `/plugin install pr-review-toolkit@claude-plugins-official`.

`.claude/settings.json` lets the skill run routine `gh`, `git` and `task` commands without prompting, and denies merging PRs, closing issues, merge commits, pushes or force-pushes to `main`, and staging everything at once (`git add .`, `-A`, `--all`, `-u`, `git commit -a`): files are staged by name. The Fix stage's `gh pr edit`, `git range-diff` and `git -c sequence.editor=true rebase origin/main` aren't on the allow list yet, so they prompt until you add them.

**Review and merge:** for a second opinion, open a fresh Claude Code session on the PR branch and run `/pr-review-toolkit:review-pr` or `/code-review`. To ask for changes, leave review or line comments, then add the `agent-fix` label to the PR; the next `/issue-sdlc` run picks it up first. (A "Request changes" review won't work: Claude Code opens PRs as your account, and GitHub doesn't let an author request changes on their own PR.) When you're satisfied, tick the PR's reviewer checklist, mark it ready and use **Rebase and merge**; the checklist stands in for an approval, which GitHub won't let you give your own PR. If a session dies mid-stage, remove `agent-working` from the issue or PR by hand and re-add its stage label (`agent-ready`, `agent-build` or `agent-fix`).
