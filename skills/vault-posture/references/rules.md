# vault-posture rule catalogue

Every finding carries a `rule_id` from this table. Remediation commands are **drafted for an operator to run**; the skill never runs them. Fill `<placeholders>` from the finding's `object` and `evidence`. When a row says "No catalogue command", describe the change in words and tell the operator to confirm the exact command in the Vault documentation.

## Quotas

| Rule | Severity | Meaning | Remediation (for an operator to run) | Caveats |
| --- | --- | --- | --- | --- |
| VP-QUOTA-001 | medium | No rate-limit quota exists anywhere in the cluster. One noisy or compromised client can saturate Vault for everyone. | `vault write sys/quotas/rate-limit/global rate=<requests-per-second>` (size from current peak traffic plus headroom) | Set the rate from observed load (`vault.core.handle_request` metrics), not a guess: too low a global rate causes an outage. Health, seal-status and unseal paths are exempt by default. |
| VP-QUOTA-002 | medium | No lease-count quota exists (Enterprise). Nothing stops a client or mount from creating leases without bound, which is how lease explosions start. | `vault write sys/quotas/lease-count/global max_leases=<limit>`, or tune Vault's built-in one: `vault write sys/quotas/lease-count/default max_leases=<limit>` | Enterprise only: on Community the scope is `unsupported` and this rule is not judged. Enterprise 1.16+ creates a global `default` quota of 300000 leases on new installs; untouched it counts as no quota (`evidence.builtin_default`), because 300000 is the scale lease explosions reach. A `default` deliberately left at 300000 can't be told apart: keep that limit under another quota name. Count current leases per mount first so the limit doesn't block normal issuance. |
| VP-QUOTA-003 | low | Quotas of this type exist, but every one is scoped to a path, namespace or role (`evidence.paths`). Traffic outside those paths has no ceiling. | `vault write sys/quotas/<quota_type>/global <rate=…\|max_leases=…>` alongside the scoped ones | Scoped quotas are good practice; this only asks for a cluster-wide backstop as well. |
| VP-QUOTA-004 | info | Rate-limit quotas exist, but requests they reject are not written to the audit log. A client being throttled is invisible to the SOC. | `vault write sys/quotas/config enable_rate_limit_audit_logging=true` | Adds audit volume during an incident, which is usually when it's wanted. |

## Security

| Rule | Severity | Meaning | Remediation (for an operator to run) | Caveats |
| --- | --- | --- | --- | --- |
| VP-SEC-001 | high | A root token generation (`sys/generate-root/attempt`) or recovery token generation is in progress (`evidence.progress` of `evidence.required` key shares). Anyone completing it gets a root or recovery token. | If nobody on the operator team started it: `vault operator generate-root -cancel` (recovery: `vault operator generate-root -generate-recovery-token -cancel`), then treat it as an incident and review the audit log for who called `sys/generate-root/attempt`. | A planned break-glass ceremony also shows up here: confirm with the key holders before cancelling. |
| VP-SEC-002 | medium | A rekey of the unseal keys (`sys/rekey/init`) or recovery keys is in progress. | If not planned: `vault operator rekey -cancel` (recovery keys: `vault operator rekey -target=recovery -cancel`). | A stale, forgotten rekey blocks the next planned one; a live one is an expected part of key-holder rotation. |
| VP-SEC-003 | low | The barrier encryption key (`evidence.term`) was installed more than `evidence.threshold_days` days ago (`evidence.age_days`). | `vault operator rotate` | Online and non-disruptive. Rotation is cheap; also set an interval (VP-SEC-004) so it doesn't need remembering. |
| VP-SEC-004 | info | Automatic barrier key rotation has no time interval (`evidence.interval_seconds` 0) or is disabled; the key rotates only after `evidence.max_operations` encryptions or by hand. | `vault write sys/rotate/config enabled=true interval=<e.g. 2160h>` | The operation-count trigger alone almost never fires on a typical cluster. |

## Plugins

| Rule | Severity | Meaning | Remediation (for an operator to run) | Caveats |
| --- | --- | --- | --- | --- |
| VP-PLUG-001 | low | An external plugin (`evidence.plugin_type`/`evidence.plugin_name`) is registered without a version, so which binary runs can't be tracked or pinned across upgrades. | `vault plugin register -sha256=<sha> -version=<semver> <type> <name>`, then `vault plugin reload -plugin=<name>` | Registering a versioned entry doesn't switch mounts to it: each mount pins its plugin version (`vault secrets tune -plugin-version=…`). |
| VP-PLUG-002 | info | External (non-builtin) plugins are registered (`evidence.plugins`). Each one runs third-party code inside Vault's trust boundary. | No catalogue command: review each plugin's source, owner and update cadence; deregister unused ones with `vault plugin deregister -version=<v> <type> <name>` after confirming no mount uses them. | Inventory for supply-chain review, not a defect. |

## Auth roles

Role findings carry `namespace`, `evidence.mount` and `evidence.role`; `object.path` is the role's API path. Add `-namespace=<namespace>` to every command for a role outside the root namespace. On these auth methods a `vault write` to an existing role updates only the fields given; the operator should `vault read` the role before and after.

| Rule | Severity | Meaning | Remediation (for an operator to run) | Caveats |
| --- | --- | --- | --- | --- |
| VP-ROLE-001 | high | Logging in through this role yields a root token (`evidence.token_policies`), or this token role can mint root tokens (`evidence.allowed_policies` / `allowed_policies_glob`). Whoever satisfies the role's bindings owns the cluster. | Auth role: `vault write <object.path> token_policies=<least-privilege policies>`. Token role: `vault write <object.path> allowed_policies=<policies>` (and drop any glob that matches `root`). | Root tokens should only come from `vault operator generate-root` during a break-glass event, then be revoked. Confirm who relies on the role before changing it. |
| VP-ROLE-002 | medium | A JWT role (`role_type=jwt`) checks only `bound_audiences`. Any token the issuer mints for that audience logs in: for GitHub Actions, any workflow in any repository that requests that audience. | `vault write <object.path> bound_subject=<exact sub>` or `bound_claims=<json>` with `bound_claims_type=string`, e.g. `{"repository":"org/repo","ref":"refs/heads/main"}` | OIDC (browser) roles are not flagged: redirect URIs and the user's login constrain them. |
| VP-ROLE-003 | medium | `bound_claims_type=glob` and a bound claim contains `*` (`evidence.wildcard_claims`), e.g. `repository: org/*` accepts every repository in the org, forks and new repos included. | Replace the wildcard with explicit values (a list is allowed): `vault write <object.path> bound_claims=<json without wildcards>` | A glob is sometimes intended (environments, branches). Pair it with a second exact claim such as `repository_owner_id`. |
| VP-ROLE-004 | low | `verbose_oidc_logging=true`: ID tokens and claims are written to the Vault server log. | `vault write <object.path> verbose_oidc_logging=false` | Meant for short debugging sessions only; Vault warns when it is enabled. |
| VP-ROLE-005 | high | A Kubernetes role binds `bound_service_account_names=*` and `bound_service_account_namespaces=*` with no namespace selector: every pod in the cluster can log in. | `vault write <object.path> bound_service_account_names=<sa> bound_service_account_namespaces=<ns>` | Check which workloads use the role first (audit log `auth/<mount>login` with this role). |
| VP-ROLE-006 | medium | A Kubernetes role accepts any service account name (`evidence.any_service_account`) or any namespace (`evidence.any_namespace`). | Narrow the wildcard side: `vault write <object.path> bound_service_account_names=<sa>` or `bound_service_account_namespaces=<ns>` (or `bound_service_account_namespace_selector=<label selector>`) | A namespace selector is not flagged: it is how `*` is meant to be narrowed. |
| VP-ROLE-007 | medium | An AppRole has `bind_secret_id=false`: the role ID alone authenticates, so it is a long-lived static password bounded only by CIDR (`evidence.secret_id_bound_cidrs`, `evidence.token_bound_cidrs`). | `vault write <object.path> bind_secret_id=true`, then deliver secret IDs to the workload (response wrapping recommended) | Breaks the current login flow until the client sends a secret ID: coordinate with the app owner. |
| VP-ROLE-008 | low | AppRole secret IDs never expire (`secret_id_ttl=0`); a leaked secret ID stays valid until someone revokes it. | `vault write <object.path> secret_id_ttl=<e.g. 720h>` | Existing secret IDs keep the TTL they were issued with; rotate them after the change. |
| VP-ROLE-009 | low | The role issues periodic tokens (`evidence.period_seconds`) with no explicit max TTL: renewed on time they never expire. On token roles `evidence.orphan` shows whether they also escape parent revocation. | `vault write <object.path> token_explicit_max_ttl=<e.g. 720h>` (token roles: `token_explicit_max_ttl=…`) | Periodic tokens suit long-running services; the explicit max TTL just bounds them. |
| VP-AWS-001 | high | An AWS IAM role binds `bound_iam_principal_arn` to `*` or to an ARN with a wildcard account (`evidence.wildcard_arns`, e.g. `arn:aws:iam::*:role/*`): an IAM identity in any AWS account, including an attacker's own, can log in. `evidence.account_narrowed` is true only when `bound_account_id` is checked through an inferred EC2 instance. | `vault write <object.path> bound_iam_principal_arn=arn:aws:iam::<account-id>:role/<role-name>` | `bound_account_id` does not narrow a plain IAM login; it is checked only with `inferred_entity_type=ec2_instance`. A wildcard role name inside one trusted account (`arn:aws:iam::<account-id>:role/app-*`) is not flagged. |
| VP-AWS-002 | high | An AWS EC2 role has no bound that pins an account or instance (`bound_account_id`, `bound_vpc_id`, `bound_subnet_id`, `bound_iam_role_arn`, `bound_iam_instance_profile_arn`, `bound_ec2_instance_id`); only `evidence.bound_region` or `evidence.bound_ami_id`, if anything. Any instance in any AWS account in that region, or launched from that (possibly public) AMI, can log in. | `vault write <object.path> bound_account_id=<account-id>` (better also `bound_iam_role_arn=<instance role ARN>` or `bound_vpc_id=<vpc-id>`) | Current Vault refuses EC2 roles with no bound at all; older roles may still have none. A private, unshared AMI does pin an account, but the AMI ID alone doesn't show that. |
| VP-AWS-003 | low | An AWS IAM role has `resolve_aws_unique_ids=false` with exact principal ARNs (`evidence.bound_iam_principal_arn`): Vault compares names, so a principal deleted and recreated with the same name (by anyone who can create IAM principals in that account) still logs in. | `vault write <object.path> resolve_aws_unique_ids=true` | Vault resolves the ARNs at write time with its own AWS credentials (`iam:GetUser`/`iam:GetRole`), so the write fails without them; if it is refused on the existing role, recreate the role with the field set. Wildcard ARNs are never resolved and are not judged here. |
| VP-AWS-004 | low | An AWS EC2 role has `allow_instance_migration=true`: Vault accepts a reused identity document whose pending time changed, so a stolen document from a stopped-and-started (or migrated) instance can log in again. | `vault write <object.path> allow_instance_migration=false` | Only needed while instances move between hosts; leave it off otherwise. `evidence.disallow_reauthentication` shows whether reauthentication is blocked altogether. |
| VP-GCP-001 | high | A GCP IAM role binds `bound_service_accounts=*` with no `bound_projects`: a service account in any GCP project, including an attacker's own, can log in. `evidence.allow_gce_inference` shows whether GCE instances can also log in through the role with their service account. | `vault write <object.path> bound_projects=<project-id>` (better: `bound_service_accounts=<sa>@<project-id>.iam.gserviceaccount.com`) | Vault looks up the service account with its own GCP credentials at login, so the caller's project must let Vault's identity read it; an attacker controls that grant in their own project, so it is no barrier. Vault accepts this binding on current versions. |
| VP-GCP-002 | high | A GCP GCE role has no `bound_projects` and no exact `bound_service_accounts`: only `evidence.bound_zones`, `bound_regions`, `bound_instance_groups` or `bound_labels`, if anything. Any project can reuse those names, so a GCE instance in any GCP project that matches them can log in. | `vault write <object.path> bound_projects=<project-id>` (or `bound_service_accounts=<instance sa>@<project-id>.iam.gserviceaccount.com`) | Vault fetches the instance with its own GCP credentials at login; as for VP-GCP-001, the attacker's project can grant that read. A service account email belongs to one project, so an exact one pins the role and is not flagged. Roles written by very old plugin versions with only singular legacy fields (`project_id`, `bound_zone`) may be flagged when they are pinned; read the role to confirm. |
| VP-GCP-003 | medium | A GCP IAM role binds `bound_service_accounts=*` within `evidence.bound_projects`: every service account in those projects can log in, including ones created later and default service accounts any workload there runs as. | `vault write <object.path> bound_service_accounts=<sa>@<project-id>.iam.gserviceaccount.com` | Intended when a project is dedicated to the workloads that use this role; then say so rather than flag it as a defect. |
| VP-GCP-004 | low | A GCP IAM role sets `max_jwt_exp` above the 900s default (`evidence.max_jwt_exp_seconds`): Vault accepts signed JWTs valid that long, so a stolen JWT stays replayable longer. | `vault write <object.path> max_jwt_exp=900` | Only `iam` roles take `max_jwt_exp`; GCE identity tokens have a lifetime set by Google. Clients must request a JWT whose `exp` fits the new limit. |
| VP-AZURE-001 | medium | An Azure role binds `bound_service_principal_ids=*` or `bound_group_ids=*` (`evidence.wildcard_field`) with the other identity field empty and no `bound_subscription_ids`, `bound_resource_groups` or `bound_scale_sets`: any managed identity or service principal in the tenant set in `auth/<mount>config` can log in. `evidence.bound_locations`, if set, only limits logins to VMs in those regions, which any subscription in the tenant can create. | `vault write <object.path> bound_service_principal_ids=<object-id>` (or `bound_group_ids=<group-id>`, or `bound_subscription_ids=<subscription-id> bound_resource_groups=<rg>`) | The tenant is fixed by the mount's config, so identities from another tenant are never admitted; that is why this is medium, not high. The config itself (tenant, client ID, client secret) is not read. Vault treats `*` as a wildcard only when it is the field's sole entry. |
| VP-AZURE-002 | low | An Azure role binds no specific service principal or group: `bound_service_principal_ids` and `bound_group_ids` are both empty, or both `*`. Vault 1.20 and later (azure plugin v0.21.0+) refuse every login through the role, so it is dead config; Vault 1.19 and older admit any identity in the tenant that matches its remaining bounds (`evidence.bound_locations`, `bound_subscription_ids`, `bound_resource_groups`, `bound_scale_sets`). | `vault write <object.path> bound_service_principal_ids=<object-id>` (or `bound_group_ids=<group-id>`); if nothing uses the role, `vault delete <object.path>` | The script cannot see the plugin version, so treat this as medium on clusters still on Vault 1.19 or older, or running an older external azure plugin. Vault accepts such a role on write; only the login is refused. |
| VP-AZURE-003 | low | An Azure role binds `bound_resource_groups` or `bound_scale_sets` without `bound_subscription_ids`, and no specific `bound_service_principal_ids` pins the identity (`evidence.bound_group_ids` shows a group or `*`): a VM or scale set in a same-named resource group in any subscription of the tenant matches. | `vault write <object.path> bound_subscription_ids=<subscription-id>` | Vault fetches the VM or scale set with its own credentials in the subscription the client names, so only subscriptions Vault's identity can read are reachable. With workload identity (WIF) logins Vault matches the token's app ID against user-assigned identities in the bound resource groups instead of comparing the group name. |
| VP-CERT-001 | medium | A TLS certificate auth role sets no `allowed_*` name, OU or organization constraint and no `required_extensions`: any client certificate the role's trusted CA signed logs in, whoever it was issued to. `evidence.ocsp_enabled` shows whether revoked certificates are at least refused. | `vault write <object.path> allowed_common_names=<cn>` (or `allowed_dns_sans=…`, `allowed_uri_sans=…`, `allowed_organizational_units=…`, `required_extensions=<oid>:<value>`) | Intended when the CA is dedicated to this one role's clients; then say so rather than flag it as a defect. The trusted CA itself is not read or judged. Existing certificates that don't match the new constraint stop logging in: check the audit log for `auth/<mount>login` with this role first. |
| VP-CERT-002 | medium | A cert role's only name constraint is a catch-all glob (`evidence.broad_patterns`: `*`, `*.*` or a bare TLD such as `*.com` in `allowed_names`, `allowed_common_names` or `allowed_dns_sans`), so it accepts the same certificates as VP-CERT-001. | `vault write <object.path> allowed_common_names=<exact cn or *.your-domain>` (likewise `allowed_dns_sans` / `allowed_names`) | Not flagged when another field narrows the role (e.g. `allowed_organizational_units`): Vault requires every constraint to match. `*.example.com` and `web-*` are not catch-alls. |

## PKI

PKI findings need the `vault-posture-pki-reader` add-on policy; without it the `mounts` scope is `denied` and no VP-PKI rule is judged. `object.path` is `<mount>issuer/<issuer_id>` for issuer rules and `<mount>` for mount rules; `evidence.issuer_name` / `evidence.common_name` identify the issuer. Add `-namespace=<namespace>` outside the root namespace.

| Rule | Severity | Meaning | Remediation (for an operator to run) | Caveats |
| --- | --- | --- | --- | --- |
| VP-PKI-001 | high | The issuer certificate has expired (`evidence.not_after`). Nothing it signs validates, and anything still chaining to it is failing now. | Issue a replacement CA: for a root, `vault write <mount>root/rotate/internal common_name=<cn> issuer_name=<new>`; for an intermediate, generate a CSR with `vault write <mount>intermediate/generate/internal …`, have the parent sign it, then `vault write <mount>intermediate/set-signed certificate=@<file>`. Then `vault write <mount>config/issuers default=<new>`. | Revoked issuers are not judged. Clients must trust the new CA before leaves move to it. |
| VP-PKI-002 | medium | The issuer expires within `evidence.threshold_days` (default 30) days (`evidence.days_left`). | As VP-PKI-001, now, before it expires. | Leaf TTLs are capped by the issuer unless leaf_not_after_behavior=permit (VP-PKI-008), so new leaves are already getting shorter. |
| VP-PKI-003 | low | The issuer expires within `evidence.threshold_days` (default 90) days. | Plan the rotation in VP-PKI-001; root rotation needs client trust-store updates, which take time. | |
| VP-PKI-004 | low | Automatic tidy is disabled on the mount: expired certificates and revocation entries accumulate, growing storage and slowing CRL builds. | `vault write <mount>config/auto-tidy enabled=true tidy_cert_store=true tidy_revoked_certs=true interval_duration=12h` | The first tidy of a large store is heavy; run a manual `vault write <mount>tidy …` off-peak first. |
| VP-PKI-005 | low | Neither the issuer nor the mount (`config/urls`) publishes an AIA issuing-certificates URL, so clients can't fetch missing chain certificates. | `vault write <mount>config/urls issuing_certificates=<https://vault/v1/<mount>ca> crl_distribution_points=<…/crl>` | Only affects certificates issued after the change. |
| VP-PKI-006 | medium | The mount has both the CRL (`disable=true`) and OCSP (`ocsp_disable=true`) disabled: a revoked certificate can't be detected by anyone. | `vault write <mount>config/crl disable=false` (and/or `ocsp_disable=false`) | Disabling both is defensible only for very short-lived leaves (minutes); confirm that is the design. |
| VP-PKI-007 | medium | The issuer uses a weak key or signature (`evidence.weaknesses`: RSA/DSA below 2048 bits, EC below 256, SHA-1/MD5). | Rotate to a new issuer with a strong key (as VP-PKI-001, e.g. `key_type=ec key_bits=256` or `key_type=rsa key_bits=3072`). | Current Vault refuses to create such keys, so these issuers were imported. |
| VP-PKI-008 | low | `leaf_not_after_behavior=permit`: the issuer signs leaves that outlive it, which fail validation once the issuer expires. | `vault patch <object.path> leaf_not_after_behavior=err` (or `truncate`) | Use `patch`: a `write` to an issuer resets fields not given, including its name. |

## Ranking

When reporting, group in this order:

1. VP-SEC-001 (possible unauthorised root), VP-ROLE-001 (root via login), VP-ROLE-005 (any pod logs in), VP-AWS-001/002 (any AWS account logs in), VP-GCP-001/002 (any GCP project logs in), VP-PKI-001 (expired CA), VP-SEC-002.
2. VP-ROLE-002/003/006/007, VP-GCP-003, VP-AZURE-001, VP-CERT-001/002 (loose login bindings), VP-PKI-002/006/007, VP-QUOTA-001/002 (no protection from noisy clients or lease explosions).
3. VP-QUOTA-003, VP-SEC-003, VP-PLUG-001, VP-ROLE-004/008/009, VP-AWS-003/004, VP-GCP-004, VP-AZURE-002/003, VP-PKI-003/004/005/008.
4. Info: VP-QUOTA-004, VP-SEC-004, VP-PLUG-002.
